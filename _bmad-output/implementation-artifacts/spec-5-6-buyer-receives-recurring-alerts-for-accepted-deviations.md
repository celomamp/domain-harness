## Intent

**Problem:** Story 5.5 stores the acceptance's `alertIntervalHours` (integer hours, 1–8760) but nothing consumes it: no alert is ever evaluated, raised or delivered (FR-15, AD-17), so an accepted risk can quietly become permanent. The registry owns alert evaluation and delivery end to end; the Company service plays no part.

**Approach:** In `packages/contract`, add the accepted-deviation-alert surfaces: the API paths (`GET /v1/accepted-deviation-alerts`, `POST /v1/accepted-deviation-alerts/{id}/dismissal`), the `AcceptedDeviationAlert` wire shape and strict never-throw guards. In `apps/registry`, migration 0014 adds two append-only tenant-scoped tables — `accepted_deviation_alerts` (one row per raised interval boundary, UNIQUE per boundary) and `accepted_deviation_alert_dismissals` (one row per Buyer dismissal) — plus a narrow cross-tenant SECURITY DEFINER function (the 0002 lookup-role pattern) that lists tenants holding live acceptances. A new alert service computes each acceptance's interval boundaries from the registry's own injected clock (`now`), raises one alert per due boundary idempotently, lists the live (raised, not dismissed, window still open) alerts naming the Application, the Standard and the end date, and lets only the Buyer dismiss. `serve-cli` runs the raise on a plain in-process interval so the scheduler exists at run time and stays testable (`now` is a parameter). In `apps/panel`, the `accepted-deviation-alert` band (UX-DR17, DESIGN.md component spec) renders under `panel-chrome` on every signed-in surface for the Buyer: a gold `accent` fill with `ink-on-accent` `label-strong` text naming Application description, Standard id and end date, with a Dismiss control; it stays until dismissed or the end date passes, and contains no motion (the 5-second pause/hide rule is met vacuously and pinned by test).

## Boundaries & Constraints

**Always:**
- Alert evaluation and delivery live entirely in `apps/registry` and `apps/panel`; `apps/service`, `packages/core`, `packages/extractor` and `@domain-harness/gate` are untouched. No alert logic may enter a bundle (bundles are unchanged; `compile.ts` keeps carrying `acceptedDeviations` as 5.5 shipped it).
- A boundary is raised at each `starts_at + k * alertIntervalHours` (integer hour arithmetic, UTC) for k >= 1, strictly before `ends_at`, at the first scheduler evaluation with a clock `now >= boundary` while the acceptance is still live (`starts_at <= now < ends_at`). One alert per boundary forever: UNIQUE (tenant_id, acceptance_id, due_at) makes raises idempotent and catch-up (a missed tick) exact — a boundary is raised at most once. No alert at k = 0 and none after expiry: a window that closed before the next tick raises nothing.
- Both new tables mirror 0013's mechanics exactly (forced RLS with the `tenant_isolation` policy, composite FKs `(tenant_id, id)`, `GRANT SELECT, INSERT` to `dh_registry_app` only, drizzle mirrors, membership in `TENANT_TABLES`); the runtime role gains no UPDATE/DELETE anywhere. Dismissal is an INSERT into the dismissals table with ON CONFLICT DO NOTHING — append-only, idempotent.
- The cross-tenant scheduler access is the established narrow exception pattern: a NOLOGIN role (`dh_alert_scheduler`) owning one SECURITY DEFINER function (`live_accepted_deviation_alert_tenants(p_now)`) that returns only tenant ids with live acceptances; the runtime role gets EXECUTE, never membership (`assertRuntimeRoleSafe` is not changed — the scheduler role is never a runtime role). All reads and inserts for a tenant run inside `withTenant(tx, tenantId, …)`.
- `GET /v1/accepted-deviation-alerts` answers 200 `{ alerts: AcceptedDeviationAlert[] }` to every role (mirrors `listAcceptances`; no new plan gate — Community cannot hold an acceptance, so it can never hold an alert, and no plan-change route exists). A dismissal `POST` checks the role first, before the body is read and drained (mirrors `requireBuyer`): any role but the Buyer gets `role_denied`; then the body (400 `invalid_input`, subject `alertId`), then the alert's visibility in the tenant (404 `not_found`, subject `alertId`), then an idempotent insert, answering 200 `{ dismissed: true }`.
- Each listed alert names the acceptance it belongs to: `applicationName` from `applications.description` at read time, `standardId` + the stored `standardVersion`, the slot and subject, the acceptance's `end` instant, and the alert's `dueAt`/`raisedAt`. The list is live only: no dismissed alert, no acceptance whose window closed (`end > now`, registry clock), one deterministic order (dueAt asc, then id asc).
- The band follows DESIGN.md's `accepted-deviation-alert` component: gold `{colors.accent}` fill, `{colors.ink-on-accent}` in `{typography.label-strong}`, `{rounded.sm}` radius, under `panel-chrome` on every signed-in surface, for the Buyer's session (rendered only when the layout's role is Buyer; the API read stays open to every role like the acceptance records). Text: `Application <description>. Standard <standardId>. End date <YYYY-MM-DD>.` plus a Dismiss control. It is `role="status"`, and it animates or moves never — the "pause or hide if it animates or updates for more than 5 seconds" rule is satisfied vacuously and pinned by a styles test.
- Panel dismissal goes through a `useFetcher` POST to a dedicated resource action route (`/accepted-deviation-alerts/dismissals`) so the current page never navigates, then revalidates the routers; every registry refusal (outage, session end) leaves the page intact and the band in its last known state — a failed dismissal is announced as a status, never silent.
- The scheduler loop lives in `serve-cli`: one catch-up evaluation at startup, then `setInterval` at `ALERT_TICK_SECONDS` (60 s) calling the service's `raiseDueAlerts(db, new Date())`, each tick logging ids/counts only (`alerts_raised` with raised/failed counts, `alert_tick_failed` on error); the timer is cleared in the existing `stop()` handler. A failed tenant's raise never starves the other tenants (per-tenant isolation inside one evaluation).

**Never:**
- No changes to: `packages/core`, `packages/extractor`, `apps/service` (any file), `packages/gate`, `apps/registry/src/bundles/*` (the compile/payload path stays exactly as 5.5 left it), or `accepted_deviation_records` (schema, privileges, service). `AcceptedDeviation`/`AcceptedDeviationRecord` wire shapes and the bundle format are untouched — no version bump.
- No email/SMS/push delivery: the registry `mail` module gains no new caller; the alert's delivery channel is the raised record read by the panel (EXPERIENCE.md's recorded assumption: the channel is the panel, no email is assumed).
- No plan-refusal logic added: no new capability map, no plan check in the alert service or routes (the capability is enforced upstream at acceptance recording; alerts are consequences of stored acceptances).
- No pruning, editing, re-raising or expiry of alert rows (append-only; the read-time window filter is the only liveness mechanism); no batch dismissal; no dismissal by a role other than the Buyer.
- No new chromatic colors (hex/px tripwires stay), gold fill allowed on exactly two selectors: the pre-existing `.button-primary` and the new `.accepted-deviation-alert` band — the gold tripwire's allowed set is amended to both, never loosened further; no `animation`/`transition` on the band's rules; no new runtime dependency anywhere; no background-job library or external cron.
- No new table outside migrations 0014's two; no ALTER of an existing table.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| First reminder | Acceptance recorded at `start`, window live, interval N; scheduler evaluates with `now = start + N` (inclusive) | One `accepted_deviation_alerts` row (dueAt = that boundary, raisedAt = now); `raised: 1` | None |
| Nothing due yet | `now` < `start + N` (or `now` < `start`) | Zero rows; evaluation answers `raised: 0` | None |
| Repeat tick idempotent | A second evaluation at the same or later `now` with boundaries already persisted | `raised: 0`; no new rows (UNIQUE on (tenant, acceptance, dueAt)) | None |
| Expired window | Acceptance with `ends_at <= now` | No candidates, no alerts; a previously raised alert vanishes from the read (`end > now` filter) | None |
| Catch-up after downtime | Registry restarts with `now` past two boundaries of a still-live acceptance | Exactly those two boundaries inserted on the next evaluation (oldest first), none for boundaries past `end` | None |
| Multi-tenant isolation | Tenant A and B both hold live acceptances | Alerts raise per tenant under its own `withTenant` context; tenant A's read never contains tenant B's rows (RLS); a tenant error does not stop the other tenants (failed count logged) | Per-tenant failure counted, others proceed |
| GET live list | Session of any role; raised, undismissed alerts with `end > now` | 200 `{ alerts: [...] }` — Application description, Standard id + stored version, slot, subject, acceptance `end`, dueAt, raisedAt; order (dueAt asc, id asc) | None |
| GET excludes | A dismissed alert, or an alert whose acceptance expired | Absent from the response (single read under `withTenant`) | None |
| Dismiss (Buyer) | Buyer POSTs an existing alert id of their tenant | 200 `{ dismissed: true }`; one dismissal row (idempotent: a second POST answers the same with still one row) | None |
| Dismiss (non-Buyer) | Builder/Standard owner POSTs | `role_denied` before the body is read (drained); nothing written | Panel: status denial rendering the registry message |
| Dismiss unknown / foreign alert | id not an alert of this tenant (including another tenant's, invisible under RLS) | 404 `not_found` naming `alertId`; nothing written | None |
| Malformed dismissal body | missing/empty/non-UUID `alertId`, extra fields | 400 `invalid_input` subject `alertId`; nothing written | Nothing written |
| Community tenant | Any alert route called (none can exist) | Empty `{ alerts: [] }` / 404 — never a plan refusal | None |
| Band renders | Buyer session; ≥1 live alert on any signed-in page load | Gold band under panel-chrome naming Application description, Standard id, end date, with a Dismiss control; role="status"; multiple alerts render one band each | Registry outage/unavailable or session loss → no band, page unaffected |
| Dismiss in panel | Buyer uses the band's Dismiss control | `useFetcher` POSTs the resource route; band disappears after revalidation; registry failure keeps the band and the page with a status (`denial`) | No navigation, no data loss on the page behind |

**Acceptance Criteria:**
- Given an Accepted deviation with interval N recorded over [start, end), when the registry's scheduler evaluates with its own clock `now`, then exactly one alert exists per boundary `start + k*N` (k ≥ 1) with `boundary <= now < end`, none before the first boundary, none for a window that expired, and a re-run of the same evaluation raises nothing; every alert names the Application (its description), the Standard (id + stored version), the Conflict slot and subject, and the acceptance's end date, and was raised by the registry — the Company service evaluates and delivers no alert (no file of `apps/service` changes).
- Given raised alerts, when the Buyer signs in and loads any panel surface, then the gold `accepted-deviation-alert` band appears under panel-chrome naming Application, Standard and end date with an ink-on-accent label and a Dismiss control, stays after reloading the same or another page, never animates or transitions (pinned by the styles test), and disappears from the read once the acceptance's end date passes.
